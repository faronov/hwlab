# ADR 0015 — Saleae Logic 2: capture-and-export over the automation API

Status: accepted. Validated against a fake Logic 2 server (CI) and, for the
digital path, on a real original Saleae Logic (0925:3881) with real Logic 2
2.4.14 (see "Real-hardware findings"). Analog is unverified: this model has no
analog channels.

## Context

Saleae analyzers are driven through the Logic 2 desktop application. Its
automation server (gRPC, default `127.0.0.1:10430`, `--automation`) captures
into Logic 2's own buffer and hands the finished data over as files. There is
no live sample stream. hwlab already has one device class that streams
(PPK2); the Saleae is the first that does not, so it tests whether the
capture abstraction holds without vendor hacks in the core.

## Decision

- **Direct gRPC from Go**, no Python. The upstream `saleae.proto`
  (Apache-2.0, Automation API 1.0.0) is vendored in `third_party/saleae/`
  with its LICENSE/NOTICE; the stubs live in `plugins/saleae/internal/saleaepb`
  and are generated by `make proto`.
- **Capabilities.** `DigitalCapture`, `AnalogCapture`, `TimedCapture`,
  `OfflineCapture`, `ArtifactExport`. It does **not** advertise
  `LiveRawStream`; the core needed no change. (Contrast ADR 0012, where J-Link
  RTT genuinely streams.)
- **Capture flow.** `Duration > 0` -> Logic 2 timed capture; otherwise manual,
  ended by `StopCapture` when the hwlab capture is stopped. A timed capture
  ends by itself (`WaitCapture`); `WaitCapture` is never used with manual mode
  (Logic 2 forbids it). If hwlab's own timer fires first, the plugin gives
  Logic 2 3 s to finish before calling `StopCapture`; a cancel well before the
  deadline stops immediately.
- **Export, then events.** After the capture ends the plugin runs
  `SaveCapture` (`capture.sal`, artifact kind `native-capture`),
  `ExportRawDataCsv` (`raw/digital.csv`, `raw/analog.csv`) and, per configured
  analyzer, `AddAnalyzer` + `ExportDataTableCsv`. The CSVs are stream-parsed
  into the normal event model: digital -> `DigitalEdges` (so the timeline gets
  `digital.edge` events and the plot gets digital tracks), analog ->
  `AnalogBatch` (analog track), analyzer rows -> `DecodedProtocolEvent`
  (`decoded` events, plotted as an event track). Equal-nanosecond changes
  collapse to the later state because `DigitalEdges` offsets must strictly
  increase.
- **Export failures are warnings** (warn `Log` events), unless nothing at all
  could be saved or exported, in which case the capture fails.
- **Timing claims.** Logic 2 reports times as offsets from its capture start.
  The plugin anchors them at the host time the `StartCapture` RPC returned and
  reports `ClockInfo` with *no* error bounds (both unbounded) plus the
  measured RPC latency in the note: the delay between the RPC and the device
  actually sampling is not measured. A hardware-trigger test must replace this
  before any cross-device correlation precision is claimed.
- **Shared filesystem.** Logic 2 writes the files, so it must see the
  artifact directory (same host, or a shared mount). Documented; no transfer
  protocol (ADR 0005).
- **Sample rates are required.** Legal rates depend on the device model and
  enabled channels; the plugin does not guess them.
- **Config.** `digital_channels`, `analog_channels`, `digital_sample_rate`,
  `analog_sample_rate`, `digital_threshold_volts`, `glitch_filters`,
  `buffer_mb`, `channel_names`, `analog_downsample`, `save_native`,
  `analyzers` (`type: spi|i2c|uart` with `channels`, or `name:` plus
  `settings:` for any Logic 2 analyzer). See `examples/saleae-spi.yaml`.
- **CI.** `plugins/saleae/internal/fakelogic2` is an in-process Manager server
  that writes fabricated CSVs. Unit tests and an end-to-end test (built plugin
  binary -> run -> timeline -> plot -> replay without the plugin) need neither
  Logic 2 nor hardware.

## Real-hardware findings (original Saleae Logic, Logic 2 2.4.14)

- `digital.csv` is `Time [s],Channel 0,...` with the first row the initial
  state at 0 and a last row at the end of the capture; a capture with no
  activity therefore has exactly two rows. The reader anchors the first batch
  at the initial-state row; before, an idle capture produced no events and the
  run failed at the plot step.
- `ExportRawDataCsv` writes `digital.csv` as assumed.
- Data tables: UART `name,type,start_time,duration,"error","data"`; I2C and SPI
  have only the common columns until a frame appears. Rows are decoded into
  `decoded` events.
- Analyzer settings `Input Channel` + `Bit Rate (Bits/s)` (Async Serial),
  `SDA`/`SCL` (I2C) and `Clock/MOSI/Enable` (SPI) were accepted by Logic 2.
  The UART and I2C analyzers decoded real (noise) edges; SPI saw no activity.
  Protocol correctness on real bus traffic is not verified.
- Analog: Logic 2 rejects analog channels on this model with `Requested analog
  channels are unavailable`; the error is surfaced unchanged.
- Timing: StartCapture RPC latency is ~0.7 s; times are offsets from the
  capture start and the ClockInfo stays unbounded.
- A plot with nothing to draw is now a warning (`plot.ErrNothingToPlot`), not a
  failed run.

## Unverified

- Analog capture and `analog.csv` on a Logic Pro or other analog model.
- Analyzer settings other than those above, and decoded I2C/SPI payloads on a
  real bus.
- Large-capture export time (the core waits up to 30 s in `Stop`).

## Consequences

The core is untouched: the run engine already ingests events produced after
the capture ends. The cost is that no data is visible until the capture
finishes and that export of very large captures is bounded by the stop
timeout; `analog_downsample` and a shorter capture are the mitigations.
