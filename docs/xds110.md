# TI XDS110 (`xds110` plugin)

Native Go driver for the TI XDS110 debug probe (USB `0451:bef3`, found on the
standalone **LP-XDS110ET** and on LaunchPads). Linux (usbfs) and macOS (IOKit,
[ADR 0035](adr/0035-macos-iokit-usb.md); run on macOS with a stand-alone
XDS110 for the cJTAG work), no CGO. No OpenOCD,
Code Composer Studio, DSLite, xdsdfu, Python or libusb at runtime.

The wire protocol was reimplemented from observation of the real probe; OpenOCD's
`xds110.c` (GPL) was read as a protocol reference only.

Layers: `internal/usb` -> `plugins/xds110/xds` (framing, SWD link, JTAG port,
batched scan engine) -> `internal/adiv5` / `internal/jtag` -> `internal/cortexm`
(shared with ST-Link and CMSIS-DAP). Two-pin cJTAG to TI CC13xx/CC26xx adds
`internal/ti/icepick` (ICEPick-C router) and `internal/adiv5/jtagdp` (JTAG-DP
link) under `internal/adiv5`, and `internal/ti/cc26xx` (identity, CCFG rules
shared with `tibsl`, ROM flash API driver); see [CC13xx/CC26xx over two-pin
cJTAG](#cc13xxcc26xx-over-two-pin-cjtag-interfacecjtag).

The LP-XDS110ET itself has **no target**. The validated target is a user-owned
CC2340 module wired to the 20-pin debug connector (silkscreen: pin 1 GND, 5 3V3,
11 nRST, 13 TMS = SWDIO, 15 TCK = SWCLK). The 3V3 pin is the probe's own
rail: it is live (3.3 V) whenever USB is connected and jumper P9 (TGT VDD) is on XDS,
with or without an EnergyTrace capture, and no command switches it (phase 27). With nothing attached, an all-zero JTAG scan and an SWD "protocol error
(-615)" are the expected result, not a probe failure; the same error also
appears when SWDIO and SWCLK are swapped, which is what happened first on the
CC2340 (0x6BA02477 appeared as soon as the two wires were exchanged). -615 on
a correctly wired CC2340 after a power cycle was a dormant SW-DP (the wire swap
above may have been the same effect); `DebugProbe.connect` now wakes it with the
ADIv5.2 dormant-to-SWD sequence through OCD_PATHMOVE and reports
`woke_from_dormant` ([note](notes/cc2340-dormant-swd-wake.md)). With
nRESET held low the CC2340's DAP gives no ACK: attach without reset.
`internal/cortexm` discovers breakpoint and watchpoint hardware from the
target (FP_CTRL, DWT_CTRL, ROM table) instead of from the architecture name;
absent units are reported as UNSUPPORTED_BY_ATTACHED_HW. Details: [support-matrix.md](support-matrix.md).

## USB layout (observed)

| Interface | Role | Endpoints | Driver |
|---|---|---|---|
| 0 / 1 | CDC (ttyACM) | 0x81, 0x01/0x82 | cdc_acm |
| **2** | **XDS110 debug protocol (claimed)** | OUT 0x02, IN 0x83 (512 B) | none |
| 3 / 4 | CDC (ttyACM) | 0x84, 0x03/0x85 | cdc_acm |
| 5 | HID, CMSIS-DAP v1 | 0x04/0x86 | usbhid |
| 6 | vendor bulk, EnergyTrace data stream (claimed only while a capture runs) | OUT 0x05, IN 0x87 | none |

hwlab claims interface 2 only. The `uart` plugin keeps working on the ttyACM
ports; the `cmsisdap` plugin lists the same physical probe through interface 5.
Both can be open at once.

## Usage

```
hwlab devices                                     # xds110/0451:bef3:<serial>
hwlab invoke xds110/0451:bef3:<serial> DebugProbe.info
hwlab invoke --yes xds110/0451:bef3:<serial> DebugProbe.clock_probe   # default rates
hwlab run --yes examples/xds110-probe.yaml                             # custom rates_hz
```

Methods: `DebugProbe` info, clock_probe, target_power, jtag_scan, connect,
ap_scan, status, halt, resume, step, wait_halt, reset (sysreset | core |
hardware), read_registers, write_register, set/clear/list breakpoint,
set/clear/list watchpoint, rtt_info, rtt_write, chip_info, icepick_info,
cc26xx_chip_erase; `MemoryAccess` read, write; `FlashProgramming` (CC23xx over
SWD, CC13x2/CC26x2 over cJTAG). Device config: `clock_hz` (100 kHz..14 MHz,
default 1 MHz), `ap`, `timeout_ms`, `interface` (`swd` default, `cjtag`),
`cjtag_format` (`oscan1` default, `oscan2`), `allow_target_power`, and the flash
permissions `allow_flash`, `allow_erase`, `allow_chip_erase`, `allow_ccfg_write`.
`HWLAB_XDS110_SIM=1` adds the SYNTHETIC `xds110/sim-xds110`.

## CC13xx/CC26xx over two-pin cJTAG (`interface=cjtag`)

CC13xx/CC26xx have no SWD. They come up in IEEE 1149.7 cJTAG, and many boards
(SONOFF ZBDongle-P: 5-pin 3V3/GND/TMS/TCK/RESET) route only TMSC and TCKC, so
a four-pin scan reads TDO as all zeros. Wiring from the XDS110 10-pin Cortex
header: pin 1 VTref -> 3V3, 2 TMS/SWDIO -> TMS (TMSC), 4 TCK -> TCK (TCKC),
10 nRESET -> RESET, 3/5/9 -> GND.

What `interface=cjtag` does on every attach:

1. leaves cJTAG, enables the probe's cJTAG property (`XDS_SET_PROPERTY` 4;
   firmware 3.0.0.32 answers -122 and activates the two-pin format anyway),
   pulses nTRST and clocks TCK for about 50 ms either side (returns a target
   still in a two-pin format to its power-up state: without it a second
   activation reads all ones), then `CJTAG_CONNECT` with format 7 (OScan1) or
   8 (OScan2);
2. every scan goes through `OCD_SCAN_REQUEST` batches and ends in
   Run-Test/Idle or Pause-IR/DR: Test-Logic-Reset is never clocked (it drops
   a 1149.7 target out of the two-pin format);
3. ICEPick-C: IDCODE (expects IR capture 0b000001), CONNECT key 0x89, control
   register 0x001000, debug TAP 0 router writes 0x110048 / 0x112048 /
   0x112148 in Pause states, BYPASS and 10 Run-Test/Idle clocks: the CPU DAP
   joins the chain between ICEPick and TDO (chain IR capture 0x011);
4. JTAG-DP (IR 4: DPACC 0xA, APACC 0xB, ABORT 0x8, IDCODE 0xE) with the
   ICEPick as one BYPASS bit; reads are collected from the following scan,
   WAIT is retried in order, a WAIT followed by an accepted request in one
   batch is an error. DPv0 has no DPIDR, so the DAP IDCODE is reported there.
   Then the shared MEM-AP and Cortex-M layers run unchanged.

If the ICEPick answers but the DAP does not join, the CCFG has closed it:
`chip_info` reports `debug_locked=true` with the ICEPick details and every
core method fails with `DEBUG_LOCKED`. `icepick_info` reports the routing
without touching the core.

Methods on a CC13xx/CC26xx: `DebugProbe.chip_info` (the shape of tibsl's
identify: chip name from FCFG1 ICEPICK_DEVICE_ID/USER_ID, P/R/P7 variant,
package, flash size, factory IEEE, CCFG summary), `icepick_info`, all core
methods, `reset` (sysreset and nRESET drop the two-pin format: the plugin
re-attaches and proves the reset by S_RESET_ST or a cleared C_DEBUGEN. The
TCK run of the re-activation right after a reset makes the boot ROM wait for
the debugger ("halt in boot": PC 0x1000118E, SP in GPRAM, the application
does not start). The plugin halts the core there and releases it
(`boot_rom_wait`, `left_boot_rom` from a PC sample), or with halt=true runs it
to an FPB breakpoint on the application's reset vector (flash word 1) and
reports `at_reset_vector`), and `FlashProgramming`
info, ccfg_info, read, verify, backup, erase (region | bank), program,
restore with the tibsl rules:

- backup: the whole flash read twice through the MEM-AP without halting the
  core, identical SHA-256 required, stored 0600 under
  `$HWLAB_HOME/artifacts/cc26xx-flash` with a manifest bound to
  ICEPICK_DEVICE_ID, USER_ID, factory IEEE and flash size;
- erase/program/restore (CC13x2/CC26x2 only): device opened with
  `allow_flash`/`allow_erase` (+ `allow_ccfg_write` for the CCFG sector),
  tibsl's tokens (`program-flash`, `restore-flash`, `erase-flash-region`,
  `bank-erase`, `confirm_config=modify-ccfg`), `backup=` of this chip; the
  resulting CCFG is checked with tibsl's lockout rules (plus: a blank CCFG
  counts as a debug lockout) and refused unless `ccfg_override=allow-bsl-lockout`;
- the flash itself is written by the ROM flash API (driverlib: ROM_API_TABLE
  0x10000180 entry 10 -> FlashSectorErase [5], FlashProgram [6]) run on the
  halted core with interrupts masked, a BKPT stub at 0x20000000, the stack
  below 0x20001000 and an 8 KiB buffer at 0x20001000; the flash cache (VIMS)
  is off meanwhile and FLASH_CFG.DIS_STANDBY is cleared after each call. Only
  changed sectors are erased, the CCFG sector last, every sector is read back.
  The target is reset afterwards (`reset_after=false` leaves it halted);
- bank erase writes TI's default security block into the CCFG (debug, TAPs and
  bootloader enabled, current backdoor kept; IMAGE_VALID_CONF stays erased);
- `DebugProbe.cc26xx_chip_erase`: the ICEPick chip erase test TAP (port 21,
  IR 0x1, DR 0x22) erases everything without the DAP, the recovery for a
  locked chip; needs `allow_chip_erase` and `confirm=icepick-chip-erase`.
  Procedure from OpenOCD's `cc26xx_chip_erase` (tested by its author on a
  CC2650); not run on hardware by hwlab.

Measured on the CC2652P: 1 MHz reads 20 KiB/s (full 352 KiB backup 34 s),
8.5 MHz 90 KiB/s (8 s); evidence in
[notes/xds110-cjtag-cc2652p-results.md](notes/xds110-cjtag-cc2652p-results.md). CC26x4 (CCFG in its own sector) is not supported for
writes; the ICEPick/DAP path is the same.

```
D=xds110/0451:bef3:<serial>
hwlab invoke $D DebugProbe.icepick_info -a interface=cjtag
hwlab target identify --plugin xds110 --device <serial> --config interface=cjtag
hwlab invoke --yes $D FlashProgramming.backup -a interface=cjtag -a clock_hz=4000000
hwlab target flash program --plugin xds110 --device <serial> --config interface=cjtag \
    --config allow_flash=true --config allow_erase=true --path fw.bin --token program-flash \
    --arg backup=$HOME/.hwlab/artifacts/cc26xx-flash/cc26xx-flash-<ieee>-<sha>.bin --yes
```

## Clock

`SET_TCK` takes a delay count and the reply carries no rate. Accepted values
were 100 kHz .. 14 MHz; host-timed rates come out 5-15 % below the nominal value
because the burst includes USB overhead. No precision is claimed.

## Target power (DANGEROUS)

**The LP-XDS110ET cannot switch its target power.** On hardware id 0x23,
`DebugProbe.target_power` returns `UNSUPPORTED_BY_ATTACHED_HW` and sends nothing:
`XDS_SET_SUPPLY` (0x32) is acknowledged with success but the 3V3 pin stays 3.3 V
(measured with a multimeter, off / on 3300 mV / on 2500 mV, see
[phase 27](notes/phase27-lp-xds110et-target-power.md)). The pin is the probe rail
selected by the manual jumper P9: XDS = probe rail, EXT = the target supplies itself
(0.1 V with nothing attached). A hard power cycle needs an external switch
([ADR 0033](adr/0033-power-switch.md)).

On the stand-alone XDS110 (hardware id 0x21, the only variant with a programmable
supply; UNVERIFIED, no such probe is attached) the method is still available:
enabling needs the device option `allow_target_power: true` at open time **and**
`confirm="enable-target-power"` with `millivolts` (1800..3600); the supply is
switched off again when the device is closed.

## EnergyTrace

PROTOCOL_PARTIAL, range 0 only. The command sequence and the 256 kSPS stream
format were reverse engineered from real USB traffic of the official TI tool
(used as a behavioural oracle only; no TI or GPL code was copied) and are written
up with confidence labels in [xds110-energytrace-protocol.md](xds110-energytrace-protocol.md).

* Start a capture with `capture_start` / `hwlab run` on `xds110/<id>` with the
  device option `allow_target_power: true` (confirmed with `--yes`). This gate is
  conservative: the stream does not switch the 3V3 pin (it is live with P9 on XDS
  regardless), but the unknown start commands are not fully understood. Without the
  option nothing is sent. Example: `examples/xds110-energytrace.yaml`.
* Samples are 256 kSPS current only (voltage is not measured, no energy), streamed
  into artifact chunks, timestamped from the stream-start command with a measured
  clock bound. Lost packets (sequence gaps) are counted as dropped batches and put
  on the timeline; a probe that disappears mid-capture ends the capture with an
  error event and no stop commands.
* While a capture runs the probe's debug calls return FailedPrecondition; the
  debug channel is reconnected afterwards. A debug-only experiment on a probe that
  can also capture must set `control: true` on the device.
* Verified live on a standalone LP-XDS110ET (fw 3.0.0.32): 10 s, 5 min and 10 min
  captures with no lost packets, repeated starts, cancel, unplug during a capture
  and recovery by serial. A user-owned CC2340 board is wired to the 20-pin debug
  connector (pin 1 GND, 5 3V3, 11 nRST, 13 TMS, 15 TCK); it draws about 6.95 mA.
  Pulling its 3V3 wire gave +3.4 uA (zero offset), reconnecting gave a 115 mA
  inrush, so starting the stream powers that pin (voltage not measured). The
  absolute accuracy is **not** verified against a calibrated load, and the ranges
  other than 0 are not decoded. SWD/JTAG to that board did not attach yet.
* `usbcap` gained a binary usbmon backend (`usbmonbin`) during this work, but
  usbmon cannot copy the payload of the high-rate endpoint; the payload was
  captured with a usbfs ioctl shim instead.

## RTT (target memory)

**`rtt_info` and RTT capture verified on hardware** (LP-XDS110ET + CC2340
running zigbee-rs: control block at `0x20004bd0` found with
`rtt_search_size=0x9000`, a 28-line boot log and a 338-line, 140 s Zigbee join
log captured). `rtt_write` and re-attaching after a reset *during* a capture are
simulator-tested only; `rtt_info` currently reports empty channel names. The plugin
reads SEGGER-compatible RTT buffers straight from target SRAM through the shared
engine (`internal/rtt`, plugin glue in `internal/rtt/rttplugin`, the same code
the hardware-validated `jlinknative` RTT uses). No SEGGER software is involved.

* `DebugProbe.rtt_info` (safe) finds the control block and lists the up/down
  channels; `DebugProbe.rtt_write` (confirm, `data`) writes text to a down
  channel, using only its free space. Both take `rtt_address` (skip the search),
  `rtt_search_start` / `rtt_search_size` (default `0x20000000` + 32 KiB, the
  first 32 of the CC2340R5's 36 KiB SRAM; widen it explicitly if the block lives
  higher) and `rtt_channel` (default 0).
* RTT capture: `StartCapture` records up-channel lines as `log` events on stream
  `rtt` (source `xds110-rtt`; a line containing "error", "warn" or "debug"
  gets that level).
  Extra keys: `rtt_wait_ms` (wait for the firmware to set up its block, default
  3000), `rtt_poll_min_ms` / `rtt_poll_max_ms` (back-off polling, default 5/100).
  The control block is re-validated periodically and searched again after a
  target reset. Lines are stamped on host receive, not by the target.
* **Which stream a capture records** (the `stream` key): `stream: rtt`, or any
  `rtt_*` key without `stream`, records RTT. No `stream` and no `rtt_*` key, or
  `stream: energytrace`, records EnergyTrace exactly as before (so existing
  EnergyTrace experiments are unchanged). `stream: energytrace` together with
  `rtt_*` keys, or any other value, is refused.
* The device lock is held for one poll at a time, so debug calls (status, halt,
  memory reads, ...) interleave with a running RTT capture. RTT and EnergyTrace
  captures exclude each other on one probe (FailedPrecondition). A *separate*
  `hwlab invoke` process cannot claim the probe while a capture runs (BUSY), so
  reset the target before starting the capture.
* CC23xx: every RTT access leaves SACI first, exactly like `MemoryAccess.read`,
  so `rtt_info` works on a target waiting in the boot ROM and a capture follows
  the target through a reset. With `saci_exit: none` the AHB-AP stays closed:
  `rtt_info` fails with `SACI_ACTIVE`, and a capture ends after a reset.
* The LP-XDS110ET also advertises `RTT` and `LiveRawStream`, so in `hwlab run`
  a debug-only device needs `control: true` (see `examples/xds110-probe.yaml`).

```
hwlab invoke xds110/<id> DebugProbe.rtt_info -a rtt_search_size=0x8000
hwlab invoke --yes xds110/<id> DebugProbe.rtt_write -a data=ping
hwlab lab capture --device fw=xds110/<id> --set fw.stream=rtt --set fw.rtt_channel=0 --duration 10s
```

MCP: `capture_start` with `devices: [{alias: fw, plugin: xds110, device: <id>,
config: {stream: rtt, rtt_channel: 0}}]`; `device_invoke` with
`capability: DebugProbe, method: rtt_info`.

## Not implemented

Flash outside CC23xx (SWD) and CC13x2/CC26x2 (cJTAG); four-pin JTAG debug
(the probe's format 1 is used for chain scans only); ICEPick wait-in-reset
(a reset-and-halt at the reset vector over two-pin cJTAG); EnergyTrace
voltage/energy/other ranges, SWO/trace, Windows.
