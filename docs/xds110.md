# TI XDS110 (`xds110` plugin)

Native Go driver for the TI XDS110 debug probe (USB `0451:bef3`, found on the
standalone **LP-XDS110ET** and on LaunchPads). Linux only, no CGO. No OpenOCD,
Code Composer Studio, DSLite, xdsdfu, Python or libusb at runtime.

The wire protocol was reimplemented from observation of the real probe; OpenOCD's
`xds110.c` (GPL) was read as a protocol reference only.

Layers: `internal/usb` -> `plugins/xds110/xds` (framing, SWD link, JTAG port)
-> `internal/adiv5` / `internal/jtag` -> `internal/cortexm` (shared with ST-Link
and CMSIS-DAP).

The LP-XDS110ET itself has **no target**. The validated target is a user-owned
CC2340 module wired to the 20-pin debug connector (silkscreen: pin 1 GND, 5 3V3,
11 nRST, 13 TMS = SWDIO, 15 TCK = SWCLK). The 3V3 pin is the probe's own
rail: it is live (3.3 V) whenever USB is connected and jumper P9 (TGT VDD) is on XDS,
with or without an EnergyTrace capture, and no command switches it (phase 27). With nothing attached, an all-zero JTAG scan and an SWD "protocol error
(-615)" are the expected result, not a probe failure; the same error also
appears when SWDIO and SWCLK are swapped, which is what happened first on the
CC2340 (0x6BA02477 appeared as soon as the two wires were exchanged). With
nRESET held low the CC2340's DAP gives no ACK: attach without reset.
`internal/cortexm` discovers breakpoint and watchpoint hardware from the
target (FP_CTRL, DWT_CTRL, ROM table) instead of from the architecture name;
absent units are reported as UNSUPPORTED_BY_ATTACHED_HW. Details: [support-matrix.md](support-matrix.md).

## USB layout (observed)

| Interface | Role | Endpoints | Driver |
|---|---|---|---|
| 0 / 1 | CDC (ttyACM) | 0x81, 0x01/0x82 | cdc_acm |
| **2** | **XDS110 debug protocol (claimed)** | OUT 0x02, IN 0x83 (512 B) | none |
| 3 / 4 | CDC (ttyACM) | 0x84, 0x03/0x85 | cdc_acm |
| 5 | HID, CMSIS-DAP v1 | 0x04/0x86 | usbhid |
| 6 | vendor bulk, EnergyTrace data stream (claimed only while a capture runs) | OUT 0x05, IN 0x87 | none |

hwlab claims interface 2 only. The `uart` plugin keeps working on the ttyACM
ports; the `cmsisdap` plugin lists the same physical probe through interface 5.
Both can be open at once.

## Usage

```
hwlab devices                                     # xds110/0451:bef3:<serial>
hwlab invoke xds110/0451:bef3:<serial> DebugProbe.info
hwlab invoke --yes xds110/0451:bef3:<serial> DebugProbe.clock_probe   # default rates
hwlab run --yes examples/xds110-probe.yaml                             # custom rates_hz
```

Methods: `DebugProbe` info, clock_probe, target_power, jtag_scan, connect,
ap_scan, status, halt, resume, step, wait_halt, reset (sysreset | core |
hardware), read_registers, write_register, set/clear/list breakpoint,
set/clear/list watchpoint; `MemoryAccess` read, write. Device config:
`clock_hz` (100 kHz..14 MHz, default 1 MHz), `ap`, `timeout_ms`,
`allow_target_power`. `HWLAB_XDS110_SIM=1` adds the SYNTHETIC `xds110/sim-xds110`.

## Clock

`SET_TCK` takes a delay count and the reply carries no rate. Accepted values
were 100 kHz .. 14 MHz; host-timed rates come out 5-15 % below the nominal value
because the burst includes USB overhead. No precision is claimed.

## Target power (DANGEROUS)

**The LP-XDS110ET cannot switch its target power.** On hardware id 0x23,
`DebugProbe.target_power` returns `UNSUPPORTED_BY_ATTACHED_HW` and sends nothing:
`XDS_SET_SUPPLY` (0x32) is acknowledged with success but the 3V3 pin stays 3.3 V
(measured with a multimeter, off / on 3300 mV / on 2500 mV, see
[phase 27](notes/phase27-lp-xds110et-target-power.md)). The pin is the probe rail
selected by the manual jumper P9: XDS = probe rail, EXT = the target supplies itself
(0.1 V with nothing attached). A hard power cycle needs an external switch
([ADR 0033](adr/0033-power-switch.md)).

On the stand-alone XDS110 (hardware id 0x21, the only variant with a programmable
supply; UNVERIFIED, no such probe is attached) the method is still available:
enabling needs the device option `allow_target_power: true` at open time **and**
`confirm="enable-target-power"` with `millivolts` (1800..3600); the supply is
switched off again when the device is closed.

## EnergyTrace

PROTOCOL_PARTIAL, range 0 only. The command sequence and the 256 kSPS stream
format were reverse engineered from real USB traffic of the official TI tool
(used as a behavioural oracle only; no TI or GPL code was copied) and are written
up with confidence labels in [xds110-energytrace-protocol.md](xds110-energytrace-protocol.md).

* Start a capture with `capture_start` / `hwlab run` on `xds110/<id>` with the
  device option `allow_target_power: true` (confirmed with `--yes`). This gate is
  conservative: the stream does not switch the 3V3 pin (it is live with P9 on XDS
  regardless), but the unknown start commands are not fully understood. Without the
  option nothing is sent. Example: `examples/xds110-energytrace.yaml`.
* Samples are 256 kSPS current only (voltage is not measured, no energy), streamed
  into artifact chunks, timestamped from the stream-start command with a measured
  clock bound. Lost packets (sequence gaps) are counted as dropped batches and put
  on the timeline; a probe that disappears mid-capture ends the capture with an
  error event and no stop commands.
* While a capture runs the probe's debug calls return FailedPrecondition; the
  debug channel is reconnected afterwards. A debug-only experiment on a probe that
  can also capture must set `control: true` on the device.
* Verified live on a standalone LP-XDS110ET (fw 3.0.0.32): 10 s, 5 min and 10 min
  captures with no lost packets, repeated starts, cancel, unplug during a capture
  and recovery by serial. A user-owned CC2340 board is wired to the 20-pin debug
  connector (pin 1 GND, 5 3V3, 11 nRST, 13 TMS, 15 TCK); it draws about 6.95 mA.
  Pulling its 3V3 wire gave +3.4 uA (zero offset), reconnecting gave a 115 mA
  inrush, so starting the stream powers that pin (voltage not measured). The
  absolute accuracy is **not** verified against a calibrated load, and the ranges
  other than 0 are not decoded. SWD/JTAG to that board did not attach yet.
* `usbcap` gained a binary usbmon backend (`usbmonbin`) during this work, but
  usbmon cannot copy the payload of the high-rate endpoint; the payload was
  captured with a usbfs ioctl shim instead.

## Not implemented

Flash (belongs to target-specific layers), JTAG-DP link and TI ICEPick routing
(chain scan only), EnergyTrace voltage/energy/other ranges, SWO/trace, macOS/Windows.

## Tests

`go test -race ./plugins/xds110/...` (unit and synthetic Sim);
`HWLAB_XDS110_HW=1 go test -tags hardware -count=1 -v ./plugins/xds110/`
(real probe, no target needed); unplug test:
`HWLAB_XDS110_UNPLUG=1 ... -run HWUnplugReplug` (needs a person). Replay fixture:
`testdata/real-xds110-probe` (serial sanitized), evidence:
`testdata/real-xds110-evidence/evidence.json`.
